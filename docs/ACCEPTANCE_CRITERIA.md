# Proposed prototype acceptance criteria

## Current status

The PostgreSQL backend currently passes `npm run lint` for 23 ES modules and the complete integration suite with 47 tests, 47 passed and 0 failed. Phase 3 covers 31 nested scenarios for stockpiling/pooling, sale decisions, consignment, transport, custody, dispatch/receipt, recovery inventory and genealogy; the combined suite also covers Phase 1/2 integrity and regression cases. Migrations 003, 004 and 005 rollback/reapplication is verified. Criteria below that concern payments, merchant gold trading, frontend/offline workflows, production rollout, broad pilot acceptance or blockchain remain future work unless the implementation status above explicitly says otherwise.

## Domain coverage

- **AC-01 — Site and hole relationships:** a site can contain multiple holes and more than one independent hole operator. Landowner, permit-holder and operator relationships are separately typed and effective-dated; recording them does not claim legal verification.
- **AC-02 — Independent Dora selection:** more than one Dora can be associated with a site. A processing event identifies the actual facility used and can produce multiple output batches.
- **AC-03 — Event separation:** production, allocation, processing, entitlement, sale, payment, assay and custody are distinguishable records. Ownership/entitlement is not inferred from custody, payment or QR scan.
- **AC-04 — Measurement source of truth and ownership:** batch records have no competing quantity fields; all declared, measured and pilot-verified observations come from the measurement ledger with source/entry party, time, original value/unit, and canonical grams. Each measurement set has exactly one valid typed owner; database constraints reject zero/multiple owners, orphan context, owner/batch mismatch and owner reassignment. Measurement observations cannot be updated, deleted or moved to another set; corrections append a linked observation. Differing observations remain visible.
- **AC-04a — Trade quantity semantics:** proposed transaction quantity, accepted trade quantity, seller declaration and buyer measurement are distinct. A line can preserve a discrepancy while counterparties accept a negotiated quantity. Physical inventory deduction is a separate movement and may occur in partial shipments.
- **AC-04b — Unit/precision:** mass is stored as canonical grams at `NUMERIC(20,6)` plus original entered value/unit and conversion version. Automated checks do not treat decimal scale as instrument accuracy; pilot-approved unit and rounding rules are recorded.
- **AC-04c — Production allocation sets:** one production event can output multiple batches; each output has one allocation chain with complete revisions; one set can contain multiple beneficiaries, and a beneficiary can appear across outputs. A set is entirely quantity-based or entirely share-based, never mixed. A quantity set explicitly names one output observation; the approval event names and authorizes that same observation through the pilot-authorized reviewer role. No latest-observation selection occurs. Declared, measured and verified observations remain distinguishable, conflicting values remain visible, and later correction/dispute requires a new allocation revision and approval rather than retargeting. Which observation kinds qualify remains a pilot decision. `PENDING`, `PROVISIONAL`, `DISPUTED`, `REJECTED`, `APPROVED` and `WITHDRAWN` remain distinguishable; corrections append complete revisions. Database constraints and serialized approval enforce basis totals and at most one current-approved revision per chain. Allocation does not imply entitlement or custody.
- **AC-05 — Route A lineage:** a miner's gold sale to a local merchant can be linked to a purchase line and batch; merchant aggregation and resale to a larger merchant preserve source purchase links.
- **AC-06 — Route B lineage:** Dora-retained residue remains linked to its processing inputs; multiple residue batches can enter a stockpile/consignment; multiple consignments can contribute to a recovery event; recovered gold preserves all contributing input references.
- **AC-06a — Residue sale:** a Dora-to-recovery-facility residue sale is distinct from dispatch, receipt, custody and payment, and its sold quantities can be reconciled to the shipped consignment items.
- **AC-06b — Dora intake measurement authority:** stockpile intake cites an unsuperseded `MEASURED` or `VERIFIED` observation from the exact source processing output, batch and measurement set. `DECLARED` or superseded measurements cannot establish inventory, and the posted quantity equals the selected observation; database enforcement and tests cover these conditions.
- **AC-06c — Receipt reconciliation and correction:** current accepted, disputed and rejected claims remain separately visible, and total current presented quantity cannot exceed accepted dispatched quantity net of reversals. Partial receipts remain valid; duplicate idempotency retries apply once and competing claims serialize. Receipt corrections append linked evidence, fully reverse prior accepted transfer legs, and post replacement inventory only when accepted. Recovery genealogy uses only current accepted receipt observations; a receipt already cited by immutable recovery genealogy cannot be revised.
- **AC-06d — Residue-sale mismatch resolution:** conflicting seller and buyer accepted quantities remain immutable and unresolved. A linked successor proposal requires fresh acceptance from both counterparties at the same quantity before acceptance; duplicate decisions do not overwrite evidence, and the agreed amount cannot exceed eligible residue inventory.
- **AC-07 — No false pooling attribution:** when a pooled recovery has no agreed defensible allocation basis, the system shows aggregate output and contributing sources without assigning exact recovered quantities to individual miners.
- **AC-08 — Trade facts:** gold purchase/resale records distinguish declared weight, measured weight, assay, agreed price, payment and custody. Local merchant, recovery facility and larger merchant participation remain distinct.
- **AC-08a — Payment coverage:** the same payment API accepts gold-trade and residue-sale parents. Partial confirmations, failures, reversals and corrections append linked events; net confirmed settlement is derived by currency and original amounts remain visible.
- **AC-08b — Payment currency integrity:** each parent transaction has one currency; a PostgreSQL `BEFORE UPDATE OF currency_code` trigger and application-role column permissions reject changing it after insertion, even before a payment exists. A wrong-currency parent is corrected through a reasoned successor transaction. Composite database foreign keys reject a payment currency different from its parent and an event currency different from its payment. No KES default or currency conversion is assumed in the MVP. If conversion is later approved, original and converted values, both currency codes, rate and conversion time remain explicit.
- **AC-08c — Trade-linked inventory cap:** both `gold_trade_line` and `residue_sale_line` may be referenced only by accepted physical OUT postings for the current accepted line revision; the paired IN has no commercial-line reference. Database deferred checks, serialized on the parent/line chain before inventory guards, require cumulative OUT less valid linked reversals across the correction chain to be no greater than the current accepted quantity. A correction lowering accepted quantity cannot be accepted while net movement exceeds it. Adjustments cannot bypass the cap; accepted quantity, physical movement, payment and custody remain independent facts.
- **AC-09 — Gold-only scope:** user-visible choices, documentation and reports do not claim gemstone or other-mineral support.

## Access and audit

- **AC-10 — Multi-role identity:** one person can perform multiple scoped roles without duplicate person entities; a user's access can be revoked and every command is checked server-side.
- **AC-11 — Commercial boundaries:** an unrelated participant cannot access another party's price, payment, identity evidence or private notes. Counterpart access is limited to fields agreed for the transaction.
- **AC-12 — Audit/correction:** changes, approvals, rejection, permission changes and corrections retain actor, timestamps, reason/context and links to prior records. Accepted history is not silently erased.
- **AC-12a — Concurrent audit sequence:** events have per-aggregate sequences (no global sequence claim). Concurrent appends to one stream serialize under lock; cross-stream commands lock stream keys in stable order; duplicate idempotency keys return one result and stale versions conflict.
- **AC-12b — Checkpoint limits:** an independent verifier detects changed/deleted/reordered entries through the latest independently held checkpoint. Tests and UI do not claim integrity for an uncheckpointed tail or physical truth of an event.
- **AC-13 — QR privacy:** a QR value contains an opaque, revocable token; scanning without permission does not expose protected details.

## Offline behavior

- **AC-14 — Local persistence:** a command saved offline survives app restart and is visibly marked device-only until server acknowledgement.
- **AC-15 — Idempotent retry:** retrying the same client mutation ID and payload applies the operation at most once and returns the original result. Reusing that ID with a changed payload is rejected.
- **AC-16 — Conflicts:** stale custody, material quantity or inventory commands produce an explicit conflict/review result; no last-write-wins overwrite occurs.
- **AC-17 — Acknowledgement:** server acceptance has a durable receipt and can be recovered after a lost response. An offline or server-accepted event is never shown as blockchain-committed without a ledger receipt.
- **AC-18 — Offline access scope:** cached data and offline commands are limited to the device user's approved scope; logout/revocation behavior is defined and tested.
- **AC-18a — Assisted capture:** a participant without a personal smartphone can be recorded by an authorized recorder. The record distinguishes actual participant (or unresolved state), recorder, source, occurrence time, entry time, evidence and acknowledgement status. The recorder is never shown as the participant by default.
- **AC-18b — Acknowledgement and paper:** pending/not-obtained/declined/disputed acknowledgements remain visible and are not participant approval. Paper-originated records can be transcribed later only under the approved pilot process; paper time and transcription time are distinct and transcription does not imply consent or accuracy.

## Inventory and reconciliation

- **AC-24 — One inventory journal:** stockpiles, consignment transit, recovery facilities, merchants and custodian inventory accounts use one IN/OUT movement journal. There is no second writable stockpile ledger or independently editable balance.
- **AC-25 — No double count and valid movement shape:** dispatch atomically posts equal stockpile OUT + consignment IN per batch; receipt posts accepted consignment OUT + facility IN. A deferred database trigger enforces the reference matrix: transfer legs pair per batch and use one context mode; transformation OUTs reference matching inputs of the header event and INs matching outputs; adjustments use same-batch/location count evidence only; opening balances are evidenced IN-only; reversals point to accepted original lines with opposite direction and no extra context references. A line reference is metadata for its one posting, not an additional posting; manifests and residue-sale shipment mappings never post inventory. Per-header duplicate transfer legs, cross-event input/output links and unbalanced transfers are rejected. Failed transactions leave no partial movement.
- **AC-26 — Derived nonnegative balance and reconciliation:** balance equals accepted IN minus OUT by batch and location. Concurrent movements lock the same balance-key guards and cannot both consume the same available stock; commercial cap checks first serialize on the gold-trade or residue-sale parent/line chain. Every accepted movement preserves nonnegative balances; failed validation rolls back all lines. Reversal lines offset exact original lines and cannot exceed unreversed amounts; other corrections append supported adjustment postings. Physical count discrepancies create reasoned adjustment postings, identify a discrepancy without asserting fraud/theft, and do not overwrite source history. Partial or disputed receipts remain in transit/review until reconciled.

## Ledger and independent verification (conditional)

- **AC-19 — No sensitive public payload:** automated checks demonstrate personal identifiers, coordinates, assay details, prices, payments and documents are excluded from any public-chain payload.
- **AC-20 — Commitment:** an independent verifier can recompute an accepted event commitment using documented schema/canonicalization version and authorized payload/salt.
- **AC-21 — Corrections:** a correction creates a new commitment linked to the original; old ledger history remains unchanged.
- **AC-22 — Receipt state:** database acceptance, submission, network commit and failure are separately visible. A worker retry/outage cannot duplicate the domain event.
- **AC-23 — Independent network:** if a permissioned network is used, at least one independently administered participant can verify selected commitments and the agreed endorsement/custody policy. Otherwise label the capability a database-backed hash-linked audit prototype, not an operational distributed blockchain.

## Suggested automated verification

For remaining pilot scope, add tests for allocation approval policy, parent/payment currency integrity behavior as used by future payment commands, both merchant routes and payment parents, shared-device and paper transcription, offline restart/reconnect, dispute handling, property-based lineage, canonicalization/hash/checkpoint verification, privacy payload review, and recovery/backup. The current combined integration suite uses synthetic data and covers production/allocation constraints, QR, movement/currency/audit integrity, Phase 3 recovery genealogy, idempotency and migration rollback/reapply. Passing software tests does not validate a local business practice, assay, legal relationship or participant agreement.

## Pilot exit decision

The pilot owner should review criteria, unresolved field assumptions, user feedback, data quality, synchronization reliability, security/access review and operating cost before expanding scope. Passing software tests alone does not validate a business practice, assay, measurement, legal relationship or participant agreement.
