## Phase 6 implementation status (verified 2026-11-19)

The database-backed tamper-evidence prototype is implemented in additive migration `011_audit_checkpoints.sql`; migrations 001–010 are preserved. Checkpoints immutably cover selected audit stream IDs, sequence numbers and heads. Authenticated creation uses an idempotency key and records creator, timestamp and request provenance. The transactional outbox is claimed with expiring leases, retries recoverable failures, records append-only verification attempts and recovers interrupted work. `POST /api/v1/audit/checkpoints` creates a checkpoint and `GET /api/v1/audit/checkpoints/{checkpointId}` rechecks authorization and returns both saved processing state and live verification. The worker runs with `npm run audit:checkpoint-worker`. The UI distinguishes database acceptance, processing verification, covered history, the unanchored tail and the unimplemented external commitment.

The in-process verifier checks the manifest, each covered stream prefix, sequence continuity and stored heads; it separately reports later tail consistency. It detects altered, deleted or reordered covered entries, invalid checkpoint data and mismatched heads. A consistent rewrite of an uncovered tail may remain undetected. Checkpoints and streams are stored in the same PostgreSQL trust boundary, so this is not independent external verification and does not protect against an operator who can rewrite the database. Signing, separately administered checkpoint custody, an external verifier and blockchain/network deployment are not implemented.

Verification on 2026-11-19: backend lint passed for 30 ES modules; the dedicated PostgreSQL `_test` suite passed **55/55** with 0 failures, including migration rollback/reapplication 003–011 and Phase 1–5 regressions; client lint passed; TypeScript and Vite production build passed; client unit tests passed **3/3**; Chromium browser tests passed **2/2**. The outbox recovery test covers an abandoned lease, duplicate execution and retry after a recoverable interruption. These automated results do not constitute independent custody, deployment or field acceptance.

## Delivery rule

The milestone definitions below describe scope and acceptance criteria; implementation status is stated in the Phase 1/2/3/4/5/6 summaries and Stage 7 Part 1 report above. Phases 5 and 6 technical slices and Stage 7 Part 1 readiness artifacts are implemented. Deployment, field acceptance, independent checkpoint holding and the remaining Stage 7 pilot work are incomplete. Participant-dependent decisions in the [decision log](DECISION_LOG.md) remain unresolved and must be answered before their affected rules are treated as pilot policy. Do not turn unresolved assumptions into defaults. Each future implementation stage should ship a reviewable vertical slice with migrations, API/UI, permissions, observability and automated tests appropriate to its scope.

## Stage 2 — sites, holes, production and Dora processing

- **Scope:** sites, holes, effective-dated party relationships, multiple independent processing facilities per site, multiple production outputs, output-specific allocation chains and complete homogeneous-basis revisions/reviews, material batches, typed measurement-set ownership/observations, assisted-capture provenance, processing inputs/outputs, residue retention and opaque QR lookup.

## Stage 6 — tamper-evidence prototype and conditional ledger pilot

- **Scope:** append-only per-aggregate audit streams, sorted row locking, deterministic event canonicalization, salted commitment utility, database checkpoint creation and in-process verification, outbox worker, failure handling and receipt display. A separate network pilot is conditional.
- **Dependencies:** Stage 1 audit envelope; selected event allowlist; approval of payload sharing, hash/key procedures, participant governance and independent verification criteria. Operational Fabric/Besu deployment needs explicit pilot approval.
- **Deliverables:** first a database-backed hash-linked prototype; only if approved, a test permissioned network with separately controlled organizations and a documented chaincode/endorsement policy.
- **Acceptance criteria:** concurrent same-stream appends form one ordered sequence; cross-stream transactions lock consistently; there is no global-order claim; the database verifier validates the stored covered prefix and the UI states the later unanchored-tail limit; correction produces a new linked commitment; database acceptance and network commitment are visibly separate.
- **Automated tests:** concurrent checkpoint creation and stream append; immutable records; payload alteration, deletion, reordering, invalid manifest and sequence/head mismatch; valid checkpoint and later-tail behavior including rewritten uncheckpointed history; outbox retry, duplicate execution and expired-lease recovery; authorization, privacy, migration rollback/reapplication and Phase 1–5 regression coverage.
- **Known risks:** false confidence from hashes, metadata leakage, key loss, node concentration, network overhead and lack of a willing independent operator. Retain the signed-database alternative if consortium value is not demonstrated.

## Stage 7 — pilot hardening and evaluation

- **Scope:** selected-site deployment, user training, accessibility/language review, monitoring, backup/restore, security review, support and feedback; no automatic widening to all locations.
- **Dependencies:** preceding stages and explicit pilot participant agreement; hosting and support owners; reviewed data access/retention policy; if ledger is used, completed governance and outage exercises.
- **Deliverables:** bounded pilot release, support/runbook, measured feedback, defect and risk register, and recommendation to continue, change or stop.
- **Acceptance criteria:** participants complete agreed end-to-end scenarios in real connectivity conditions; data visibility matches approved matrix; data restore and offline reconciliation are demonstrated; disputed/incorrect records can be corrected without erasure; pilot owner reviews evidence before expansion.
- **Automated tests:** full critical-path end-to-end suite; regression/security/accessibility checks selected for the product; backup-restore verification; load and queue-recovery checks sized from observed pilot volumes.
- **Known risks:** onboarding burden, literacy/language fit, disputed practices, connectivity, physical evidence quality and operational cost may outweigh the traceability benefit.

## Suggested sequencing gates

- Validate domain terms and role visibility with a small set of participants before building workflow-specific rules.
- Complete a vertical path through each route before broadening reports or dashboards.
- Demonstrate offline sync and correction before collecting consequential production/trade records.
- Demonstrate independent verification and participant governance before calling the design a distributed blockchain system.
- Reassess scope, cost, data sensitivity and participant benefit at the end of each stage.
